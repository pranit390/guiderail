GuideRail blueprint

Guide first. Guard second.

A voice coach for Google tools. It points at the next step on the live screen, follows the user across Cloud Console, IAM and Gmail, and checks every form against company policy before they click Create. It never clicks for them.

0Defaults taken

The last grilling round (Q1–Q10) has no answers yet, so this blueprint uses the recommended answer for each. Change any of them and the affected sections move with it.

  • Q1 Goal → Journey → Session → Step. "Tour" and "workflow" are not used.
  • Q2 A Policy is a document. A Rule is one checkable condition. A Violation is a Rule failing.
  • Q3 Each Rule has a severity of warn or block. "Block" flags the Create button and never disables Google's real button.
  • Q4 A fixed list of Blocker types, with Gemini's generic detection as the fallback.
  • Q5 Requester and Approver are both guided.
  • Q6 GuideRail drafts messages. The user always clicks Send.
  • Q7 Two builders. A owns the extension; B owns the server, rules, sandbox and pitch.
  • Q8 Voice goes through a Cloud Run relay to the Vertex Live API. No API keys anywhere.
  • Q9 A dedicated GCP project, with every resource carrying the Org Labeling Policy's 5 labels.
  • Q10 TypeScript everywhere.

Why it's shaped this way

Gemini picks what, code finds where

Gemini calls highlight({text:"Create service"}). The content script finds the element in the page. Gemini never returns pixel coordinates, which is the pattern TipTour uses.

Policy checks are plain code

Rules are JSON and checked locally in about 1 ms on every field change. That keeps the demo reliable on camera. Gemini only compiles Policies and judges the fuzzy rules.

The side panel owns state

Chrome kills an idle background worker after about 30 s. The side panel stays open across tab switches in the window, so the voice session and Journey live there.

No keys, Vertex only

The browser never holds a credential. Cloud Run uses its service account to reach Vertex. A security team has nothing to object to.

3MVP demo flow

The one end-to-end story we build, rehearse and record. About 3.5 minutes across 4 apps and 2 people.

  1. Requester · Chrome
    Installs GuideRail. It signs in anonymously and silently, and a sandbox org is created with the Org Labeling Policy already loaded.
  2. Requester · console.cloud.google.com (signed out)
    Presses ⌘⇧K. The side panel opens and the user says the Goal.
    "I want to deploy my app to Cloud Run."
    Blocker not_signed_in is detected, so GuideRail starts a Detour: "First, sign in. Top right." It highlights the button, and the user types their own password.
  3. Requester · Cloud Console
    Project picker, then Cloud Run, then Create service. Each Step is highlighted and spoken, and moves on when the user clicks.
  4. Requester · Cloud Run
    Blocker permission_denied is detected.
    "You need Cloud Run Developer on this project. I'll draft a request to your admin."
    Gmail compose opens pre-filled with the role, project, reason and an Approver link. The user clicks Send.
  5. Approver · second Chrome profile · Gmail → Approver page → IAM
    Opens the link. GuideRail starts an Approver Journey with the role already chosen. The admin picks Owner.
    "Hold on. Policy says least privilege. Grant Cloud Run Developer instead."
    The admin fixes it and grants. The audit log records violation → resolved.
  6. Requester · back in Cloud Run
    The Journey resumes from Firestore.
    "Access granted. Picking up where we left off."
    Service account Step: the name must start with sa-, no Owner role, no key download.
  7. Requester · Cloud Run create form · Labels step
    Guide first: GuideRail explains the 5 required labels and shows a Suggested labels card (environment asked, application from the service name, component=api, owner=pranit, managed-by=manual) with copy buttons.
    "Your org needs 5 labels here. I've suggested values. Is this prod or dev?"
    Then guard: the user skips one and moves toward Create. Five block Violations show. Create is outlined red with the reason, and GuideRail speaks and highlights the Labels section. The user types owner=pranit@example.com.
    "Label values can't contain @ or dots. Use your first name: owner=pranit."
  8. Requester
    All Rules pass. "You're good to deploy." The user clicks Create. The Goal is detected (service URL shown) and the Journey completes.
  9. Admin dashboard · Firebase Hosting
    1 Journey, 4 apps, 2 Detours, 4 Violations prevented, about 6 min in total.

Judge path

Judges get the same story on our hosted copies of the Cloud Run form, IAM grant page and a Gmail-style compose page, with no install, GCP account or second person needed. The page loads the same overlay bundle with a <script> tag, and a "Switch to Approver" button stands in for the second profile.

4.3 The Step loop

read_page→ highlight→ speak→ wait_for_user→ complete_step↺

wait_for_user resolves when

  • click: a capture-phase click on the highlighted element or inside it
  • url_change: webNavigation.onHistoryStateUpdated, since the console is a single-page app
  • element_visible: a MutationObserver sees the expected text appear
  • field_value: an input event matches the expected value
  • After a 45 s timeout, GuideRail asks "Stuck? Want me to show it again?"

When highlight returns not_found

  • Returns the 5 closest names to Gemini, which picks one or rephrases
  • Scrolls through the page's scroll containers and retries once
  • Last resort: a screenshot (tabs.captureVisibleTab) is sent to Gemini, and it answers with a description, not coordinates
  • Never guesses a click target

4.7 Tab switch, reload and resume

Tab switch

tabs.onActivated: the background worker tells the side panel. The router re-points to the new tab's port, injecting the content script if it's missing, and the Journey continues.

Page reload

The content script reloads. On load it asks the side panel "active Journey?", gets the current Step and highlights it again. Voice is unaffected.

Side panel closed or next day

A new WebSocket sends the stored resumptionHandle. If it has expired, the server opens a fresh session and seeds it with a Journey summary from Firestore.

One Cloud Run service, guiderail-api (Node 22, TypeScript). Auth middleware on every route: verify the Firebase ID token and App Check token, load users/{uid}, check the rate limit.

5.2 Deploy

gcloud run deploy guiderail-api --source api/ --region us-central1 \
  --service-account sa-guiderail-api@PROJECT_ID.iam.gserviceaccount.com \
  --timeout 3600 --session-affinity --min-instances 1 --concurrency 40 \
  --labels environment=dev,application=guiderail,component=api,owner=pranit,managed-by=gcp

The service account has roles/aiplatform.user and roles/datastore.user and nothing else. --timeout 3600 keeps the WebSocket open for long sessions. --min-instances 1 avoids a cold start during judging.

7Policy rules (seeded)

From the example Org Labeling Policy plus two IAM rules for the Approver scene.

Guide before guard

Every Rule carries a guide as well as a check. When the user reaches a Rule's section, GuideRail first explains and suggests (format, examples, a value worked out from context). The check runs afterwards on every change and only speaks when something is wrong. Suggestions: owner from the user's first name or team, managed-by=manual for console creates, application from the service name matched to canonical apps, component from the resource type, and environment always asked.

8Data and storage

Firestore

orgs/{orgId}
  policies/{id}   name, sourceText, published
  rules/{id}      scope, check, severity, message
  journeys/{id}   uid, goal, status, steps[], detours[],
                  resumption?, updatedAt
  audit/{id}      journeyId, type(step|violation|resolved
                  |blocker), ruleId?, app, ts
  approvals/{id}  requester, approver?, role, resource,
                  reason, status, expiresAt
users/{uid}       orgId, role(admin|member), anonymous

In the browser

  • chrome.storage.managed: Rules pushed by IT through Google Admin (mocked with a local file in the demo)
  • chrome.storage.session: {journeyId, stepIndex, resumptionHandle}
  • Firestore offline cache (IndexedDB, side panel): Journeys and audit, synced when online
  • Transcripts stay local. Only Steps and audit events sync, which is the privacy point in the pitch.

Security rules

  • Members read their own org's Rules and write only their own Journeys and audit events
  • Only admins write Policies and Rules
  • Approvals are read by link ID and written only by the server
